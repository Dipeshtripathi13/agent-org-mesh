02

mesh_app grants — enforced by postgres, not application code

The append-only guarantee on audit_log and policy_revisions isn't a check in server.ts. The mesh_app role was simply never issued UPDATE or DELETE — there's nothing in application code to bypass.

REVOKE UPDATE, DELETE ON audit_log FROM mesh_app; appears in schema.sql as documentation of intent — the grant was never issued in the first place, so the REVOKE is a belt-and-braces no-op, not the actual mechanism.
03

the ask pipeline — POST /api/agent/ask

What actually happens between a real question and a real answer. Four stages — tool selection narrows which connected surfaces get invoked, tool invocation is mechanical against whatever that narrowed set is, disclosure is deterministic code, and a model only ever writes prose from what's already been authorized. Two separate, narrowly-scoped model touchpoints; neither one makes a disclosure decision — and which model runs both of them is resolved per-person, not hardcoded to one vendor.

One adapter serves ChatGPT and any self-hosted/open-source model behind the same wire protocol — pointing OPENAI_BASE_URL at a local server is the entire "add a new model" change, no new code. mainEligible (orthogonal to api_family) additionally gates which catalog entries the "Set up my agent" picker offers as a main agent — claude-code has a real adapter but is a dev tool, sub-agent-only regardless.

Live-verified against a real local model. Diego and Hana (Northbeam, ids 11 and 10) each independently registered llama-local — Ollama running llama3.2:1b (1.3 GB, GPU-accelerated, chosen specifically because it was already on the machine and small enough to leave headroom on 16 GB). Hana asking about Diego produced a genuine markdown-formatted synthesis in ~4.8s, not the raw-digest fallback — and along the way, llama3.2:1b wrapped its router response in markdown fences despite being told not to, which parseRelevantSurfaces's tolerant regex absorbed with zero special-casing. Diego asking about Hana correctly resolved her own registration (confirmed via ollama ps's idle-timer refreshing on that exact request) but returned "nothing disclosable" — this seed org only ever gave Diego real gatherable activity, so that's an honest data limitation, not a dispatch failure. Full setup walkthrough: docs/agent-to-agent-communication.md §15a.
Two model touchpoints, neither one a disclosure decision — and neither one hardcoded to a vendor. The router (this section) only narrows which real-world calls get made — it can under-select and just leave a surface's claims at their last-fetched freshness, never withhold anything that would otherwise be disclosed. The synthesis call (§04) only writes prose from text respond() already cleared. respond() itself stays exactly as deterministic as CLAUDE.md rule 1 requires either way — no model output ever reaches it, only claim rows, regardless of which ModelProvider resolved. Design doc: docs/agent-to-agent-communication.md §5–7, §6a, §15.
04

Per claim, per request. Deterministic: no LLM, no randomness, no clock read except the caller-supplied `now`. Same inputs, same output — always.

05

role derivation — deriveAllowedRoles()

Closes a specific vulnerability class: a requester asserting "Direct manager" that respond() then trusts at face value. Roles are computed from the org graph itself — never from anything the requester claims about themselves.

condition (from the real org graph)role granted
requesterId === targetIdSelf
target.managerId === requesterIdDirect manager
target's manager's managerId === requesterIdSkip-level
target.managerId != null && requester.managerId === target.managerIdPeer
requester.team === 'IT'IT admin
requester.managerId == null || requester.team === 'Executive'Executive

A request claiming a role outside this computed set is rejected before respond() ever runs. Functional roles (IT admin, Executive) aren't chain-relative — they're structurally who the requester is, independent of the target.

06

audit chain — hashEntry() / verifyChain()

One algorithm, imported by both the in-memory AuditLog (golden tests) and repo.ts (Postgres) — never two copies that could quietly drift apart.

verifyChain() walks any ordering of rows and detects both a tampered field and a reordered/spliced chain in one pass — recompute hashEntry(row) and compare, then check row.prevHash === previous row's rowHash.

// audit.ts — the snapshot discipline
const entry = {
  id: randomUUID(),
  snapshot: input.snapshot,        // resolved once, stored whole
  subjectNotifiedAt: input.now,    // same instant as the read — not a queued job
  prevHash: prev?.rowHash ?? null,
};
entry.rowHash = hashEntry(entry);  // never recomputed from *current* policy later
Why not recompute at read time? A stored answer is never re-derived from live policy — that would let a later policy edit silently rewrite what someone was told last Tuesday. Snapshot once, hash once, done.

"My agent" → "Ask yourself" is a real, switchable, ChatGPT-shaped chat — not a second history mechanism. One nullable column on audit_log, grouped in application code; nothing new stored.

GET /api/person/:id/conversations derives the chat list the same way: group that person's real Self-role rows by conversation_id, title = first question, updated = latest created_at — computed in application code (listConversationsForPerson), not stored, not a table.

Scope stayed deliberately narrow. Only the Self-role chat path resolves/passes a conversationId — cross-person Ask never sends one, so its behavior is byte-for-byte unchanged. The tool-selection router (§03) also doesn't get conversation context: each turn independently decides which surfaces are relevant to its own question, which stays correct even when a follow-up's topic drifts.
08

escalation detection — 3 deterministic rules, run inline

runEscalationChecks() fires immediately after every real respond() call in server.ts, reusing data the caller already fetched — no separate cron, no re-query. Same discipline as policy.ts: real structural state or nothing, never an invented signal.

ESC-COVERAGE

Zero connected surfaces

agentDeployed = true, inScopeCount > 0, connectedCount = 0. Escalates exactly what's known: nothing is connected — not a guessed blocker.

fires immediately, no age threshold
ESC-STALE-CLAIM

Connected activity gone quiet

Most recent real claim is older than the threshold. Can't distinguish "no work happened" from "token revoked" — title says "gone quiet," not "no work."

STALE_CLAIM_DAYS = 7
ESC-REPEAT-WITHHOLD

Same pair, repeatedly refused

Reads policyRef !== null specifically — not tier === CANT, which would fire for everyone (every response carries a structural CANT boilerplate item).

REPEAT_WITHHOLD_THRESHOLD = 3 consecutive real asks

path is resolved from the org graph at detection time as {'{'}personId, name{'}'}[] — the personId lets an acknowledge/resolve request check structurally whether the caller is actually on the path, rather than string-matching a name.
